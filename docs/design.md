# Design: Low-Latency Order Book Engine

## Why two implementations?
The naive implementation uses std::map which is simplier and easier to implement and bugs are less likely to hide and can use it as practical reference for the array-based version which is complex than the previous version and with manual tick-offset indexing and bounds handling, which creates more opportunities for subtle mistakes. Because agreement between the two doesn't guarantee correctness, both implementations could share the same bug on some rare edge case. I run many randomized order sequences through both and check that their resulting book state matches at every step, using the simpler version as a practical (not perfect) source of truth to catch bugs in the optimized one.

## Naive implementation (baseline)
- Data structure: std::map<Price, PriceLevel> for each side (buy/sell)
- Why this is the right starting point: 
Because highestBuy always points directly at the current best price, checking what the best bid is takes O(1) and no search needed. That pointer only moves when the current price level's orders are completely gone, at which point it re-points to the new best bid. Similarly, because each price level already holds its orders in a deque, adding a new order there just means calling push_back and no search needed, so it's O(1). When an order arrives at a price that isn't already in the tree, the map has to walk down comparing prices to find the right spot, then create a new node with a fresh deque for it and this costs O(log M), where M is the number of distinct price levels. 
- Known limitation: 
The one weak spot in this structure is canceling by order ID: since the tree is sorted by Price, not by orderId, finding a specific order would cost O(N) in the worst case — so a separate OrderId -> Price hash map is used instead, bringing cancel down to an O(1) lookup followed by a small scan of just that price level's deque.

## Optimized implementation (target)
- Data structure: array indexed by price-tick offset
- What it improves over the naive version, and why: 
The array pre-allocates a slot for every possible price, so unlike the tree, there's no difference between inserting at a new price versus an existing one — both just mean a direct lookup using the price to find the slot, which is O(1). Beyond the complexity difference, the array is also faster in practice because its elements sit contiguous in memory — the CPU's prefetcher pulls the next elements in ahead of time, before the code even asks for it. The tree's nodes, by contrast, are each allocated separately, scattered across memory, so walking the tree means the CPU can't predict the next node — a real, physical delay ('cache miss') that has nothing to do with Big-O at all. 
- Tradeoff/risk, and how it was addressed: 
The cost of a plain array is that when the current best price's slot becomes empty, finding the new best price means checking each price one at a time until an occupied one is found — in the worst case this is O(M), which happens when the book is sparse (orders spread far apart) rather than dense (orders clustered close together). Initial benchmarking confirmed this was a real, not just theoretical, problem: MatchOrder was measurably *slower* on the array (roughly 2.4x) than on the tree, in both sparse and moderately dense conditions, because the naive tree's O(log M) lookup beat the array's O(M) worst-case scan at the densities tested. This was resolved by adding a bitset alongside each price array — one bit per price level, marking occupied vs. empty — and using hardware bit-scan instructions (`__builtin_ctzll`/`__builtin_clzll`) to find the next occupied level in O(numLevels/64) word-checks plus O(1) bit-finding, instead of checking each price individually. This restored and slightly exceeded parity with the naive baseline across all measured operations, without changing any of the book's external behavior (verified by the full existing test suite passing unchanged after the rewrite).

## Correctness strategy
- **Unit tests for known cases:** 20 tests total across both implementations, covering: basic add/match/cancel, FIFO ordering within a price level, partial fills (reference-vs-copy correctness), full exhaustion (leftover quantity returned correctly), cancellation from the middle of a deque, cancellation of a nonexistent order, removal of an empty price level, array-bounds rejection for out-of-range prices, sentinel-pointer reset after a book side empties out, and array-integrity preservation after a price level empties (no corruption of neighboring price levels). Six additional tests cover the ITCH-style parser: round-trip encoding/decoding for both sides, rejection of malformed input (wrong length, unrecognized message type), correctness at integer boundary values, and end-to-end integration with the book.
- **Differential testing:** the naive implementation is simple enough to trust as a reliable reference — its logic is straightforward and easy to verify by hand, so bugs are less likely to hide in it. The optimized array-based version is more complex, with manual tick-offset indexing, bitset bookkeeping, and bounds handling, which creates more opportunities for subtle mistakes. Because agreement between the two doesn't guarantee correctness — both could share the same bug on some rare edge case — many randomized order sequences are run through both, checking that their resulting book state matches at every step, using the simpler version as a practical (not perfect) source of truth to catch bugs in the optimized one. *(Planned as an extension beyond the current unit test suite — see Planned Enhancements.)*

## Performance measurement plan
We benchmark four operations — AddOrder, MatchOrder (under both sparse and moderately dense book conditions), and CancelOrder — comparing the naive and optimized implementations using Google Benchmark, on both books reused across iterations with a bounded working set (periodic resets during untimed setup) to avoid unrelated costs like hash-table rehashing from distorting the measurement. We report median wall-clock time and CPU time per operation; CPU time is the more reliable of the two since it excludes noise from other processes running on the same machine. Sparse and dense MatchOrder scenarios are both measured deliberately, since the array's weak point (finding the next occupied price level) depends on how tightly resting orders are packed — a single density measurement would have hidden this real, measured tradeoff.

We do not control for CPU frequency scaling or use hardware CPU pinning (e.g. Linux's `taskset`/`cpupower`), since macOS (the development platform used here) does not expose this level of control to user-space applications — confirmed directly by Google Benchmark's own runtime warning ("Failed to set thread affinity") during every run. Instead, all other applications were closed and the machine was on AC power during measurement, a partial but honest substitute for the standard Linux methodology.

## Results

| Operation | Naive | Optimized | Improvement |
|---|---|---|---|
| AddOrder | 13.4 ns | 12.4 ns | ~7.5% faster |
| MatchOrder (sparse book) | 421 ns | 404 ns | ~4% faster |
| MatchOrder (dense book, 50 resting orders) | 425 ns | 408 ns | ~4% faster |
| CancelOrder (dense book) | 424 ns | 414 ns | ~2.4% faster |

All four operations show a consistent, if modest, improvement for the optimized implementation, confirmed stable across two independent runs at very different iteration scales (millions vs. hundreds of millions of iterations). A profiling pass (macOS `sample`) surfaced a real, initially-unrelated bottleneck: `orderLoc` (the OrderId → Price hash map used for O(1) cancel lookups) was dominating AddOrder's cost under sustained load due to repeated hash-table rehashing as it grew unbounded. This was fixed by pre-reserving its capacity in both implementations' constructors, and the fix was confirmed stable at up to ~500 million iterations.
